1. 最重要的一點：你的研究問題不是假問題

這點其實可以很有把握。

Trace of the Times 的原作者自己明確指出，system conditions 對 delta time 有顯著影響，而且可能在高度動態系統產生很多 false positives。他們甚至把 dynamic probing、不同 system states 的 rootkit detection、多 scenario normal model 等列為後續方向。

原論文也很清楚地說，他們的 semi-supervised detector 是拿正常 timing 建模，再把 timing shift 視為可能的 Rootkit activity。

所以你現在問的：

「我們量到的是惡意 hiding behavior，還是一般 workload / hook / instrumentation 所造成的 timing change？」

這不是事後硬創一個問題。

反而是原方法要從 proof-of-concept 走向可靠 detector 必須回答的問題。

而且 O'Neill 2025 的工作也確實往 scheduler/system-condition noise 方向走，說明「正常系統狀態干擾 timing detection」已經被其他研究者視為實際問題。

因此研究必要性這一塊，我認為是扎實的。

3. 你目前最嚴重的方法學問題：sham 其實沒有完全 matched

這是我認為投稿前最需要修的地方。

你的 Track A 現在核心論述是：

pass-through sham 控制 ftrace hook 的成本，再看 hiding 超出 sham 的 timing evidence。

概念非常合理。

但程式實際上：

caraxes_sham.c 只 hook：

filldir64

而 hiding CARAXES 的 hooks.h 安裝的是：

fillonedir
filldir
filldir64
compat_fillonedir
compat_filldir

也就是 1 個 hook vs 5 個 hooks。

如果你能證明這次 x86-64 ls workload 只會真正進 filldir64，那影響可能很小。

問題是目前 audit 只證明：

iterate_dir 每 iteration 角色組成一致；
listing output 正確；
沒有 lost event。

它沒有證明其他四個 hiding hooks 在實驗期間完全沒有被觸發，也沒有證明它們沒有帶來成本。

因此目前最安全的寫法不能是：

sham 完整控制了 Rootkit 的 ftrace hook cost。

應該改成：

sham controls the pass-through filldir64 ftrace-hook path used by the tested workload.

這兩句強度差很多。

4. 還有一個更深的問題：你的 sham 沒有控制「判斷邏輯」成本

這可能比上一點更重要。

Hiding 的 hook_filldir64() 大致是：

if (strstr(name, MAGIC_WORD))
    return true;

return orig_filldir64(...);

但 sham 是：

return orig_filldir64(...);

因此 hiding 與 sham 的差異不只是：

「有沒有真正隱藏檔案」。

還包含：

每一個 directory entry 都多做了一次 strstr() 與 branch。

換句話說，你現在得到的漂亮 separation 很可能偵測到的是：

「pass-through hook + 額外的 per-entry string matching logic」

而不是純粹：

「file hiding」。

這不代表研究沒意義。

Rootkit hiding 本來就需要執行額外邏輯，timing detector 本來就是利用這種成本。

但會影響你的「security evidence」語義。

一個完全良性的 kernel hook，只要也對 filename 做類似字串判斷、logging、policy checking，很可能落到同一方向。

所以目前把這條 axis 稱為：

Rootkit security evidence

有點太強。

比較準確的是：

hiding-associated timing evidence relative to the pass-through negative control

直到你做更強 negative control。

5. 最值得補的控制不是再跑更多相同 D6，而是做「active sham」

我認為這是最能提升論文品質的一個實驗。

你應該有至少兩種 sham：

Sham A：matched pass-through

安裝和 hiding 完全相同的五個 hooks，但是全部 pass through。

這控制 hook installation / callback framework。

Sham B：active sham

和 hiding 執行：

相同 hook；
相同 strstr(name, MAGIC_WORD)；
相同 branch 判斷；

但即使匹配也仍呼叫原始 filldir，不隱藏東西。

這樣：

unloaded
    ↓
matched pass-through sham
    ↓
active logic sham
    ↓
actual hiding

你才能真正拆出：

ftrace hooking cost
+
per-entry filtering logic cost
+
actual suppression/hiding behavior difference

如果 proposed detector 在 active sham 上仍維持低 FPR，那 Track A 的可信度會大幅提升。

如果 active sham 也被判成 Rootkit，那也不是研究失敗——反而你得到一個很重要的結果：

timing detector 實際偵測的是 hook computational behavior，而非 malicious hiding semantics。

那會讓論文定位更誠實也更有學術價值。

6. Security gate 沒有 label leakage，但有一個語義上的 circularity 風險

你的 calibration 是：

clean + sham 都是 non-attack。

security axis 是：

clean centroid → sham centroid

threshold 是：

max(clean + sham projection) + 0.01

然後超過就叫 attack。

從「資料洩漏」角度來說，這不是 attack-label leakage。

因為 hiding test data 沒進 calibration。

所以不能說它 circular 到「拿攻擊資料設定門檻，再說攻擊可分」。

這部分是合理的。

但是存在另一個問題。

你其實做的是：

anything farther than our known benign hook along this timing direction → security-positive.

這依賴一個很強的 monotonic assumption：

clean
→ benign hook
→ malicious hiding

而現實不保證所有 benign kernel modification 都排在 sham 左側。

一個更重的合法 hook 完全可能：

clean
→ sham
→ benign complex hook
→ threshold

所以這個 gate 現在可以稱為negative-control calibrated detector，但不要把「security axis」寫得好像它已經抽取出 malware-specific semantic feature。

9. 五個 boot 是很好的進步，但還不足以支撐很強的統計語言

這裡要分清楚：

你有：

但真正的獨立 experimental replication unit 是 boot。

所以有效的最高層 sample size 是：

n = 5。

這也是為什麼你用 boot-paired bootstrap 是對的方向，而不是把 1,800 batches 當獨立 observations。

可是 n=5 本身仍然非常少。

例如 proposed vs fixed OAS 的 unloaded FPR：

五個 boot 全部都是 proposed 比較好。

proposed vs fixed recall：

五個 boot 也全部比較好。

如果用最簡單的 exact paired sign test，5/5 同方向：

one-sided p = 0.03125
two-sided p = 0.0625

所以目前用 percentile bootstrap 得到不跨 0 的 CI，不代表你就可以安全地寫：

statistically significant improvement.

而不要使用「統計顯著證明」。

如果最後要投稿，增加獨立 boots 的價值其實遠高於再增加每 boot 的 batch 數。

12. max + 0.01 threshold 現在可以用，但不是一個很成熟的 statistical calibration

現在 security threshold：

calibration 中所有 clean + sham projection 最大值 + 0.01。

優點是簡單、完全 pre-specified。

但缺點很明顯：

影響。

而你已經看到了：

所以 D6-r2 的 failure mechanism 其實非常清楚：

高 context calibration
→ security threshold 高

→ false negative
→ security-negative attack 進 W50

17. Track A 最合理的結論應該收窄成這樣

我不建議現在寫：

我們證明 negative-control factorization 能有效偵測 Rootkit，並解決 timing detector 的 false positive 問題。

太大。

目前證據真正支持的是：

在單一 VM/kernel、CARAXES-like filldir file-hiding 與受控目錄/工作負載下，使用 pass-through negative-control calibration 的 security gate，可明顯降低此 benchmark 中一般 timing-shift detector 將 unloaded 與 sham 狀態誤判為 Rootkit 的情形，同時保留 93.75% hiding recall。

這句是站得住腳的。

然後再補：

但結果尚未證明對其他合法 hooks、其他 Rootkit implementations、kernel/hardware 或更廣 workload 具有相同 specificity。

這會比誇大更像一篇可信的研究。

最後，我對你這份研究的實際判斷

不是「只是在修 code」，也不是「為了有研究硬湊一個方法」。核心研究問題是真的存在。

尤其因為 Trace of the Times 自己已經把 varying system conditions / false positives 當成 practical limitation，並明確提出跨 system states 等 future work。

而你加入 negative control 的想法，從實驗設計角度是有道理的，也確實得到了一個值得研究的現象。

但是目前最需要修正的不是再把 F1 從 0.967 拉到 0.98。

而是證明：

你偵測到的真的比「有一個比 sham 稍微複雜一點的 hook」更接近 hiding-specific evidence。

如果把下一輪集中在下面四件事，整個研究會扎實很多：

matched 5-hook sham + active-logic sham，真正拆掉 hook / strstr / hiding 三種成本。
equal-information ablation/comparator，排除成果只是因為 proposed 有額外 sham calibration 和 per-boot threshold。
