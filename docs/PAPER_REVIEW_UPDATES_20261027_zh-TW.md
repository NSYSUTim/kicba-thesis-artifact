## IBLT 重複差異的原因與結果

目前實作是 `src/kicba/reconciliation.py` 的計數加 XOR 版本。各項目寫入三個互不相同的位置，解碼只從計數為 +1 或 −1 且通過校驗的儲存格取出項目。解碼完成後以殘留儲存格是否為零判定成功，尚未把回傳項目重新累計成指紋核對。

以下固定使用 `entry_00074.txt` 為 X、`entry_00934.txt` 為 Y，兩者 inode 均為 101、型態均為 8。種子為書面 4.1 節範例的 `0x0123456789ABCDEF` 與 `0xF0E1D2C3B4A59687`。

第一個反例是一端只有兩份 X，另一端為空。相同內容 XOR 後歸零，但三個位置的計數都是 2，無法開始剝離。8、256、4,096 個儲存格都解碼失敗，各殘留三格。增加容量不改變同一 X 的兩份副本寫入相同位置這件事。

第二個反例是一端兩份 X、另一端兩份 Y。當兩者寫入相同三個位置時，兩端各自的重複內容先經 XOR 抵消，表相減後計數也抵消，整張差異表為零。因此解碼器回報成功且差集為空，與真實四份差異不符。

| 儲存格數 | X 的位置 | Y 的位置 | 兩份 X 對兩份 Y 的結果 |
|---:|---|---|---|
| 8 | 3、4、7 | 3、4、7 | 差異表全零，錯誤成功且差集為空 |
| 256 | 20、247、251 | 20、247、251 | 差異表全零，錯誤成功且差集為空 |
| 4,096 | 503、2,555、3,860 | 2,068、2,555、3,319 | 僅位置 2,555 抵消，其餘四格計數為 +2 或 −2，解碼失敗 |

這些輸入的兩端指紋均不同，因此差異警報仍成立。這不是指紋碰撞，也不證明任意輸入下指紋一定不同。反例針對目前 XOR 實作，不能推成所有 IBLT 變體都無法處理重複項目。原始 IBLT 論文亦區分以 XOR 取代累加時的重複 key-value 情況，見 [Goodrich 與 Mitzenmacher，2011](https://arxiv.org/abs/1101.2245)。

正式受測案例的靜態差異中，各身分淨出現次數為 −1、0 或 +1；還原另與獨立預期差異核對，沒有觀察到錯誤成功。這是受測結果，不能改述為「容量足夠且淨次數不超過一便保證還原」。反例是離線資料結構核對，沒有經過核心隱藏模組，也沒有量得實際逃避攻擊成本。

## 計時範圍與含查詢的追加分析

補充比較中的 `wall_ns` 含程序啟動、登記、列舉、讀回、解碼與清理，不含 BPF 編譯、附掛，以及列舉前後的返回探針統計與事件身分查詢。`wall_with_coverage_ns` 另含這些查詢與窗口判讀；統計取自 `kprobe_profile`，事件身分取自 `kprobe_events` 的定義及對應事件的 `id`。具體邊界見 `phase1/run_experiments.py` 的 `snapshot()` 與 `one_scan()`，以及 `phase2/measurement.py` 的 `scan()`。

下表限 65,536 個項目、無額外負載。每開機十個主要區組，先在區組內計算合併版／診斷版，再取開機中位數；不是表中獨立耗時中位數相除。

不含查詢的降幅為 39.6%–45.1%，是事前採用指標。含查詢時降幅為 39.4%–44.7%，診斷版各開機耗時中位數為 168.13–177.52 ms，合併版為 93.29–105.44 ms；這是同一批資料的追加核對，不是新增實驗或另設採用條件。原正式實作的 4.76 倍屬另一套計時流程，維持原值。

實作改良來自合併核心狀態，減少逐項查表與使用者端讀回、清理；指紋、計入規則與同步建立 IBLT 的設計不變。不能把改善解釋成正常時已省略 IBLT、任意情境都有相同降幅，或整工具的全部資源成本都降低相同比例。

## 目前成果與尚未執行的方向

已完成的補充包括量測可靠性、指定適用條件、成本拆分與實作改良。目前仍使用專用單執行緒 C 掃描器。攻擊者只對掃描器放行、取得其他程式自己的列舉、已知種子下的適應性攻擊與金鑰保護，均尚未實作或驗證。

下一個可選研究問題是：掃描器看到完整資料，但其他程式遭到隱藏時，能否發現其他程式那次列舉的兩端差異？應先建立可核對的選擇性放行案例，再確認其他程式的兩端結果能否可靠配對。這裡記錄研究方向，沒有把規劃寫成已完成的能力。

`/proc` 可先沿用同次兩端比較。依 Linux 6.8 的 [fs/readdir.c](https://github.com/torvalds/linux/blob/v6.8/fs/readdir.c) 與 [fs/proc/base.c](https://github.com/torvalds/linux/blob/v6.8/fs/proc/base.c)，行程結束不會抹除先前已複製到使用者回傳緩衝區的紀錄，因此行程變動不直接等於兩端差異。這是原始碼推論，尚未經行程隱藏試驗驗證。若將目標延伸到兩端共同看不到的行程，才另外加入生命週期視圖與跨來源／跨時間模型。

程式庫返回後的過濾、第一端之前的新視圖及授權分類仍未展開。rkchk 保留比較缺口，沒有因這次文件更新變成必跑工作。更多環境、外部比較與容量取捨亦維持可選方向，見[目前方法與後續工作](METHOD_AND_NEXT_STEPS_zh-TW.md)。

## 重現定稿核對

```bash
python scripts/verify_paper_review_checks.py --check docs/PAPER_REVIEW_FACTS_20261027.json
```

此程式驗證目前書面 SHA-256、執行上述六個離線容量／輸入組合，並核對六份確認封存的 SHA-256，直接讀取其中 `campaign/attempts.jsonl` 重算成本。每開機十個有效配對，缺配對、重複觀察或無效品質都會拒絕，不默默排除。

需要另存結果時使用 `--output reproduced/paper_review_checks.json`，目標須為新檔。完整補充資料的原有核對入口仍為 `scripts/verify_research_updates.py --recompute`；本次沒有修改歷史報告、凍結程式或實驗鎖。
